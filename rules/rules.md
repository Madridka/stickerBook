# Project

Этот файл задаёт соглашения кода. Рабочий процесс агента и выбор проверок находятся
в [`AGENTS.md`](../AGENTS.md), доменная карта — в [`SKILL.md`](../SKILL.md).

проекта. Явные требования пользователя важнее проектных рекомендаций в рамках
системных ограничений и разрешений среды.

Вклейка

# Architecture

Использовать:

- Vue 3 Composition API
- TypeScript
- Pinia
- TailwindCSS
- Dexie.js
- vue-i18n

## Plugins

Локализация подключается через плагин:

`src/plugins/usei18n/usei18n.ts`

Плагин `usei18n` должен:

- создавать и экспортировать экземпляр vue-i18n;
- собирать переводы из JSON-файлов в `src/lang/{locale}/`;
- подключаться в `main.ts` до монтирования приложения.

# Stores

Использовать Pinia setup stores на основе Composition API:

```ts
export const useCollectionStore = defineStore('collection', () => {
  const value = ref(0)
  const total = computed(() => value.value + 1)

  return { value, total }
})
```

Запрещено использовать в stores:

- `state` option;
- `getters` option;
- store со всей логикой приложения.

Состояние, вычисления и действия возвращать явно из setup-функции store.

# TypeScript

Использовать строгую типизацию.

Обязательно:

- описывать интерфейсами публичные контракты composables и сервисов;
- указывать типы параметров и возвращаемых значений публичных функций;
- использовать `type` для импортов типов;
- не использовать `any` без обоснованной необходимости.

Для `vue-i18n` использовать простую деструктуризацию без дополнительной аннотации:

```ts
const { t } = useI18n()
```

# Code Style

Все функции создавать в виде стрелочных функций.

Использовать:

```ts
const formatValue = (value: string): string => value.trim()
```

Не использовать объявления вида `function formatValue() {}`.

# Components

Для стандартных элементов интерфейса сначала использовать готовые компоненты PrimeVue 4 (например, Button, Menu, Select), а собственную реализацию создавать только при отсутствии подходящего компонента.

Не создавать большие компоненты.

Запрещено:

- App.vue с игровой логикой
- компоненты больше 500 строк без необходимости
- store с всей логикой игры

Использовать:

views
components
composables
stores
utils

# Данные и конфигурация

Контентные данные карточек, игроков и страниц хранить отдельно от логики приложения в JSON.

Настраиваемые значения игры хранить в TypeScript-модулях каталога `src/config/`:

- `gameBalance.ts` — цены, количество карточек в паках, кулдауны, вероятности выпадения, награды и остальные параметры экономики;
- `miniGameConfig.ts` — правила, тайминги, веса выбора и координаты мини-игр;
- `stickerEngineConfig.ts` — параметры подготовки, перетаскивания и размещения стикеров;
- `albumConfig.ts` — отображение и навигация альбома;
- `catalogConfig.ts` — ограничения и схема каталога карточек;
- `runtimeConfig.ts` — технические интервалы интерфейса и анимаций.

Обязательно:

- у каждого значения должен быть один источник истины;
- не хардкодить настраиваемые значения в компонентах, stores, composables, сервисах и утилитах;
- импортировать значения непосредственно из профильного модуля без общего файла-агрегатора;
- не смешивать игровой баланс с координатами, параметрами движка и техническими интервалами интерфейса;
- все цены, кулдауны паков и вероятности выпадения изменять только в `gameBalance.ts`.

Главный экран и ключевые пользовательские сценарии должны полностью помещаться в один viewport без вертикального скролла страницы. Для этого использовать высоту viewport, гибкую раскладку и компактные отступы компонентов.

Поддержать:

- tablet около 720p
- mobile 390x844

Использовать Tailwind breakpoints.

# Assets

Не использовать Panini в названиях:

- файлов;
- папок;
- компонентов;
- переменных.

Использовать:

Album
Sticker
Pack
Collection

Исходники и визуальные материалы журналов хранить по идентификатору альбома:

`assets/game/{albumId}/{teamId}/`

Общие для альбома материалы хранить в:

`assets/game/{albumId}/main/`

Готовые карточки, которые должны раздаваться по стабильному URL без импорта в JavaScript-бандл, хранить в:

`public/{albumId}/cards/{teamId}/`

Примеры для UCL 2026/27:

- страницы и исходники: `assets/game/ucl-26-27/main/`;
- готовые карточки: `public/ucl-26-27/cards/{teamId}/`.

# Code comments

Комментировать неочевидные причины, ограничения и инварианты сложных блоков
script/template. Не пересказывать очевидный код и не добавлять комментарии ради
формального покрытия каждого блока:

```ts
// Повтор запроса использует тот же instanceId, чтобы не выдать награду дважды.
```

# Сохранения и операции

- Списание ресурса и создание результата одной игровой операции выполнять в общей
  Dexie-транзакции. Незавершённое открытие и выбор восстанавливать после перезагрузки.
- Изменения IndexedDB вносить новой версией схемы без сброса прогресса.
- При изменении сохраняемой сущности проверять её контракт в локальной БД,
  облачном снимке и трёхстороннем объединении; повторная синхронизация не должна
  повторно выдавать награды или воскрешать удалённые карточки.
- Создание оригиналов и повторок проводить через существующие операции
  `src/db/stickerLifecycle.ts`, учитывая транзакцию вызывающего кода.

# Документация и версия

При изменении пользовательских возможностей обновлять соответствующее описание
в README и запись changelog. Для пользовательских изменений сохранять SemVer:
PATCH — исправление, MINOR — совместимая возможность, MAJOR — несовместимый контракт.
Синхронизировать версию в `package.json`, `package-lock.json`, README, changelog и
OpenAPI там, где она указана. Перед правкой найти реальные места хранения версии;
не создавать новый changelog только потому, что нет отдельного файла.

Правки инструкций агента, документации, тестов и внутренний рефакторинг без изменения
пользовательского поведения сами по себе не требуют повышения версии приложения.
